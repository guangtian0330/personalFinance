## 0. 执行摘要与核心建议

**产品定位：** 一款面向普通用户的“目标驱动个人及家庭财务经营系统”（Goal-based Personal Finance OS）。后台具有企业财务核算、预算、现金流预测、资源配置与计划审计的能力；前台保持低认知负担、按需引导。

**四条支柱：**
1. **财务事实层：** 账户、交易、资产负债、预算、收支与现金流；可核对、不可凭空产生资金。
2. **规划层：** 单一/复合目标、生命周期、目标模板、未来支出事件、目标时间范围。
3. **决策层：** 安全可分配现金流、目标优先级、最多三个活跃顶层目标、可行性、分配建议、暂停与情景比较。
4. **体验层：** 渐进式问卷、可启用的功能目录、个性化首页、初学者/高级视图；用户始终可手动修改。

**建议 V1 取舍：** Web 首发、TypeScript 全栈、React + Vite + Hono、Cloudflare Workers + D1、Drizzle、Zod；模块化单体和纯 TypeScript 核心域；本地 Mock Auth 仅在开发环境，公开使用真实财务数据前必须完成正式鉴权与隔离；算法先规则后优化。

**重要澄清：** “最多三个目标”限制的是同一时刻正在分配资金的**顶层活跃目标**，不是用户能保存的全部目标，也不是每个子目标；应急流动性与必要债务支付属于系统约束，不占三个目标名额。退休可以暂停**自主新增注资**，但必须提供影响预览。

## 1. 产品愿景与边界

### 1.1 目标用户
- A：仅希望清楚收入、开销、预算的普通个人。
- B：有短中期计划的个人：换车、结婚、旅行、搬家、学费。
- C：家庭财务管理员：共同支出、家庭成员、育儿与赡养。
- D：中高阶规划用户：跨币种、投资资产、退休、现金流预测、多个竞争目标。

产品必须为 A 提供 90 秒以内可理解的入口，不能因为支持 D 就让 A 承担复杂性。初期可使用人工录入 + CSV 导入，不要求绑定银行账户。

### 1.2 产品要解决的核心问题
- “我的钱在哪里、从哪里来、花到哪里？”
- “今年是否超预算？哪些是长期固定成本？”
- “未来三年/五年/二十年的目标，需要准备多少？什么时候需要？”
- “现金不足以同时实现目标，哪项加速、延期、减速或暂停，代价是什么？”
- “结婚/买车/退休开始以后，预算结构会发生什么变化？”

### 1.3 非目标（初期不做）
- 自动执行买卖股票、转账或保险购买；系统只输出建议和用户授权后的**内部计划记录**。
- 证券价格实时交易平台、投资推荐、贷款承销、自动报税和监管意义上的投资顾问服务。
- 自动读取所有银行账户；若以后接入需另行处理安全、合规、供应商限制。
- 尝试以一个不可解释的 AI 黑箱替代财务计算规则。

### 1.4 成功指标（产品指标，非金融承诺）
- 首次使用：完成初始引导所需步骤与放弃率。
- 记账：能否输入交易并解释账户余额、类别支出、当月结余差异。
- 目标：用户能在数分钟内创建目标，看到月度需求、进度和暂停影响。
- 决策：分配建议在约束和数据变化下可重复计算，解释清楚每项分配原因。
- 数据可信：零“虚增净资产”、零跨用户读写、全部关键公式有回归测试。

## 2. 用户体验与渐进式模块启用

### 2.1 首次引导（建议 3 屏，不做长问卷）
1. **管理对象：** 个人 / 伴侣部分共享 / 家庭 / 跳过。
2. **当前最关心：** 了解开销 / 预算 / 存钱目标 / 资产与投资 / 跳过；可多选。
3. **最近的具体目标：** 旅行/买车/婚礼/购房/其他/暂时没有；可跳过。

以上回答只用于推荐模块和首页布局，不自动设置生活身份、财富情况或风险承受能力。

### 2.2 深层趣味问卷：按场景触发
- 用户探索“婚礼”时问婚礼可能性，采用五级趣味选项：无计划/顺其自然/有伴侣但未谈/认真考虑/时间确定。
- 用户探索“育儿”时只问是否需要建立与孩子有关的预算，不预设有无孩子。
- 用户探索“退休”时再问退休年龄、资金来源、预期生活方式与退休地区假设。
- 对所有敏感提问提供“跳过/暂不回答”，不据此永久隐藏功能，不作不必要推断。

### 2.3 功能展示三层
- **始终可用：** 首页、基础账本、账户、分类、收支和基础预算（可简化展示）。
- **主动建议：** 依据用户主动表达的需求推荐目标、投资、家庭成员、跨币种、退休等。
- **功能目录：** 未启用模块可以查看说明、预览用途、点击启用；UI 的“灰色”不能意味着不可点击。

Feature Manifest 应为每个功能声明 `id`、依赖、推荐条件、入口、默认状态、能力集。用户配置控制展示与导航；权限和数据隔离必须由服务端独立执行。

### 2.4 三种复杂度视图
- **简单视图：** 本月收入、支出、预算剩余、存钱目标，操作术语尽量口语化。
- **规划视图：** 目标、时间、资金缺口、未来 12 个月预测。
- **高级视图：** 资产负债、不同币种、目标算法参数、年度报表、情景模拟。

“简单/规划/高级”是展示方式，不是三套分叉的数据模型。

### 2.5 无障碍和可靠交互原则
- 支持移动网页尺寸、键盘可操作、足够对比度、清晰错误状态和表单保留。
- 用户主动控制：财务计划变动必须先预览后确认；自动推荐不自动转账。
- 每项算式都提供“为什么这样算”入口，并能追溯参数。
- 默认隐藏复杂选项，不取消用户自行查找高级功能的权利。

### 3.1 分类体系的长期标准
- **财务分类**（收入、费用、资产、负债）回答“发生了什么”。
- **目标归属**回答“为什么预留或使用这些钱”。
- **成本属性**（固定/可变、必需/可选）回答“是否可调整”。
- **人/家庭归属**回答“由谁承担、归谁所有”。
- **预算版本及人生阶段**回答“当前按哪套计划执行”。

一笔餐饮支出在退休阶段仍属于“餐饮”分类，但可以关联退休预算；绝不另造一份互不兼容的“退休餐饮交易账本”。

### 3.2 目标模板（初始默认模板列表）
- 简单目标：旅行、购车、换电脑、专业培训、紧急医疗、清偿债务。
- 复合目标：结婚（场地/仪式/礼品/住房可选）、育儿（按年龄及教育阶段）、退休（按生活类型与退休阶段）、购房（首付/税费/装修/持有成本）、迁居（证件/交通/安置/收入中断）。
- 模板本质为版本化的 `GoalTemplateDefinition`，应用于新建目标时生成 `GoalComponent`；以后更改模板不得静默修改既有用户目标。

## 4. 核心用户流程（User Journeys）

**U01 初次上手：** 访问 → 体验/注册 → 3 屏引导 → 个性化首页 → 建立首个账户 → 录入本月两三笔交易 → 看到收支和预算概览。

**U02 月度核算：** 周期收支入账/CSV 导入 → 分类 → 预算与实际差异 → 识别异常 → 用户修正类别或下期预算 → 生成月末快照。

**U03 新建简单目标：** 点击目标目录 → 选择“买车” → 目标金额、日期、已备资金、资金来源 → 系统计算最低月供资及可行性 → 用户确认激活 → 首页跟踪进度。

**U04 三个目标竞争：** 已有 3 个活跃顶层目标 → 新增重要紧急目标 → 显示候选目标与现有目标的资金需求、期限、用户重要性 → 对比“暂停目标 A / 降低目标 B / 延迟目标 C”等选项 → 用户确认 → 记录变更理由。

**U05 收入下降：** 本月收入更新 → 重新预测安全可分配金额 → 发现无法满足目标资金计划 → 生成替代方案及延期影响 → 用户选择 → 未批准前不更改正式计划。

**U06 复合目标：** 创建婚礼/育儿/退休 → 选择适用子项目 → 输入金额及阶段 → 系统汇总但不重复统计共享账目 → 形成阶段性资金计划。

**U07 买车后：** 购车目标进入执行/完成 → 支付购车款映射实际交易 → 推荐新增保险、停车、维护预算 → 目标历史仍可查询。

**U08 退休转阶段：** 用户确认退休事件 → 生成退休预算新版本 → 停止适用的工作期成本预算 → 原账本和完整历史保留 → 养老金/资产提现/兼职收入继续正常管理。

**U09 多币种：** 原币录入 → 单独保存成交汇率（若真实换汇）与估值汇率 → 统一报表选择币种 → 资产变化区分净新增资金、投资收益和汇率影响。

**U10 数据携带：** 导出标准 CSV/JSON → 验证范围与版本 → 在新安装或新账户中执行受控导入 → 核验交易数、资产及预算摘要。

**U11 家庭共享（P1）：** 创建家庭空间 → 邀请成员 → 设置共享/个人可见性 → 为共同目标按承担比例贡献 → 权限检查和审计。

## 5. 核心业务规则（拟定，待评审）

### 5.1 目标时间跨度
- 短期：剩余期限 `<= 3年`。
- 中期：`>3年 且 <=5年`。
- 长期：`>5年`。
- 日期流逝后自动重分类，不改变目标原始创建意图。以上区间是产品自定义规则，不宣称通用金融标准。

### 5.2 最多三个活跃目标
- 计数对象：`Active` 的**顶层 Goal**。`Draft/Queued/Paused/Funded/Executing/Completed/Cancelled` 不占活跃注资名额。
- 复合目标内部子项目不额外占位；一个子项目如拆为独立顶层 Goal，则单独占位。
- 应急现金储备、账单/债务强制偿付是**硬性约束或运营资金政策**，不占目标名额；用户可以选择把“建立应急金”视作目标，需明确是否与基线约束重合。
- 建议先固定最多 3 个（遵从原始设计）。是否开放 1–5 自定义属于待决议事项。

### 5.3 资金池并非真实银行账户
- `Account` 是真实/模拟金融账户；`GoalAllocation` 是资产资金用途标签（可分配额度）。
- 虚拟资金分配不能增加总资产、不能改变真实现金余额。
- 用户只能对具备适当流动性且可使用的资金进行目标承诺；不能把锁定退休资产误当买车现金。
- 目标资金不能隐式重复使用；变更归属需有转移记录和权限。

### 5.4 目标与账本关系
- 目标注资 = 计划或资金用途重标记，不等同于费用。
- 真正购买汽车、支付婚礼等才产生日常交易记录。
- 买入投资产品 = 资产交换，不等同于生活费用或投资盈利。
- 退款/撤销/更正保留审计痕迹，避免不可追溯的静默删除。

### 5.5 人生阶段转换
- 退休、育儿、结婚等事件触发**生成/激活预算版本建议**。
- 用户确认后才改变有效预算；原始账本、历史报表和回溯能力永远保留。
- 多个人生事件可以同时发生；退休不是全局排他模式。

### 5.6 风险与告警
- 账单、必要开支、已承诺债务支付和最低流动性基线优先于可选目标注资。
- 建议和模拟不得在未经确认情况下改写正式资金安排。
- 定期小波动不应导致目标反复暂停与恢复；提供重算阈值、冷却/确认机制。

## 6. 算法框架与证据管理

### 6.1 Algorithm Registry（每个算法都有文档）
每一项算法记录：`algorithmId`、版本、目的、来源类型（法规/官方/论文/工程实践/自定义假设）、公式/伪代码、参数/单位、适用范围、输入输出、舍入、边界条件、测试向量、性能和已知限制。每次产生建议保存输入快照、算法版本、权重/参数、结果与用户最终选择。

### 6.2 目标优先级
- 先确定 **强制性义务与流动性约束**，它们不参与主观重要性排名。
- 对剩余候选目标使用 MCDA 分项评分：重要性、资金期限紧迫性、延迟代价（均需给出行为锚点，如 1–5 分的明确描述）。
- 初始产品权重可以试用 `0.45 Importance + 0.35 Urgency + 0.20 DelayCost`，但标注为**待验证的产品假设**，不是文献给出的标准系数。
- 紧迫性不仅是剩余时间：还需考虑资金缺口、按当前安全现金流供资时的达成能力。已筹足目标紧迫性应显著下降。
- 对相似得分、不同权重进行敏感性分析；用户拥有最终控制权。
- 后续可用 AHP 做偏好权重学习，但问卷成本高，应为可选高级功能。

### 6.3 现金流能力与健康度
- 以未来各个月的净现金收入、必要生活费用、应支付债务、已知大额支出和最低现金底线计算安全可分配额。
- 应急现金底线可按“必要月支出 × 用户选定储备月数”计算；不是算法推断的法律/金融标准。
- `healthy / tight / critical` 基于预测现金余额和储备底线，而不只是“本月工资减支出”。
- 双计数防护：净工资已扣除的税款/养老金不得再次扣减；未到账奖金不能当成已确定收入。

### 6.4 基础资金分配（MVP）
输入：按月安全可分配金额、候选目标、优先级、目标期限、目标金额、已分配余额、资金限制、最小保护投入、最大活跃数。

处理建议：
1. 过滤 `Funded`、`Completed` 与当前不合规目标。
2. 识别必须履行的非目标财务义务，预留现金底线。
3. 计算每个目标的资金缺口与“按时完成所需的月度储蓄”。
4. 评分与用户固定优先级要求并用；生成至多 3 个活跃目标的一个或多个可行方案。
5. 如不可行，输出明确的缺口、延期或暂停方案，不伪造资金。
6. 用户确认后更新计划及资金分配记录，记录历史差异。

公式（简单无收益假设）`requiredMonthly = max(0, targetAmount - reservedAmount) / remainingMonths`。若 0 个月或目标已逾期，返回 `Overdue / ImmediateFundingNeeded`，不做除以零。

**注意：** 优先级分数决定排序和选择，不可直接等同资金比例；需要将金额、期限、账户限制与现金流组合考虑。

### 6.5 高级资金分配（P2）
- 考虑多期资源约束与生命周期，建模为 Goal Programming / LP / MILP；目标函数应显式表达相对偏好、未达成损失与延期成本。
- 可研究 HiGHS 的 MIT 许可核心及 JS/WASM 封装；先核对封装版本和依赖许可证。`glpk.js` 是 GPL-3.0，若项目可能闭源需谨慎。
- 如果有大量目标、投资收益不确定、风险偏好建模，进一步考虑动态规划或情景模拟。**不在 MVP 内做投资组合自动优化。**

### 6.6 预算与报表算法
- 月度预算偏差 `actual - budget`，不同费用符号约定要统一。
- 储蓄率需明确定义“净收入减去实际消费”与投资买卖之间的关系。
- 资产负债表：净资产 = 资产 - 负债；按日期截面估值。
- 多币种报表：原币保留、报告币种转换、汇率估值变动与现金收入区分。
- 退休计划：按年逐期模拟费用（通胀假设）、养老金收入、资产提款、退休年限和非固定回报假设；不能用一个简单的“年花销×年数”作为完整预测。

### 6.7 文献与公开技术依据（初步核实）
1. UK Government — Multi-criteria analysis manual: https://www.gov.uk/government/publications/multi-criteria-analysis-manual-for-making-government-policy
2. UK Green Book — MCDA 与敏感性分析: https://www.gov.uk/government/publications/green-book-supplementary-guidance-multi-criteria-decision-analysis/use-of-multi-criteria-decision-analysis-in-options-appraisal-of-economic-cases
3. Saaty 1986, AHP 公理基础: https://doi.org/10.1287/mnsc.32.7.841
4. Das 等，Dynamic optimization for multi-goals wealth management, J. Banking & Finance 140 (2022): https://doi.org/10.1016/j.jbankfin.2021.106192
5. Kvanli, Financial planning using goal programming, Omega 8(2) (1980): https://doi.org/10.1016/0305-0483(80)90025-0

## 7. 技术架构评审

### 7.1 推荐技术栈
- **语言：** TypeScript（前端/API/领域内核统一）。
- **Web：** React + Vite；Tailwind CSS / shadcn/ui；TanStack Query。
- **API：** Hono REST + Zod schema / OpenAPI 输出。
- **领域核心：** 纯 TypeScript，禁止依赖 React、Hono、D1、DOM 等。
- **持久化：** Drizzle ORM + SQLite；生产初选 Cloudflare D1，本地使用等效 SQLite 测试并做 D1 集成测试。
- **部署：** Cloudflare Workers + Static Assets 单服务部署。
- **身份认证：** 本地 `MockIdentityProvider`；正式可评估 Better Auth + Hono + Drizzle（具体 Workers 运行配置通过集成验证）。
- **测试：** Vitest、Playwright、API 集成、财务不变量属性测试。
- **工程：** pnpm workspaces，严格 TypeScript，ESLint/Prettier，GitHub Actions CI。

### 7.2 选择原因与边界
- Cloudflare 支持 React/Vite + Hono 的同部署方式，前端和 API 无需维护两套托管平台。
- D1 的免费层适合轻量原型（截至 2026-10 的公开资料：500 MB 单数据库、5 GB 总存储；每天 500 万行读、10 万行写；Workers Free 10ms CPU/请求、100,000 请求/天）。限额可能变动，部署前复核。
- 复杂优化/MILP 不应在免费 Worker 请求 CPU 内强行计算。可在用户端 Web Worker/WASM 做情景预览，服务端对最终保存的结果、约束和授权重新校验。
- Supabase 提供 PostgreSQL+Auth 一体化，但免费项目低活跃会自动暂停；作为备选而非首选。
- 桌面端：Tauri 封装 Web UI，若有离线需求要设计本地数据/同步。
- 微信小程序：预留 API 和领域契约复用，不承诺 DOM/React Web 组件原样复用；可评估 Taro。

**依赖方向：** `UI/API → application use-cases → domain core ← repository interfaces`；`persistence adapters → repository interfaces`。评分、金额、预算计算等领域内核不导入 UI/后端/数据库依赖。

### 7.4 业务模块关系
- `Identity / Household` → 所有私有数据的 owner/tenant 归属。
- `Accounts + Ledger` → 预算、资产、现金流、资金池的**唯一财务事实来源**。
- `Categories + Budget` → 决策引擎的必要月支出、财务计划。
- `Goals + GoalTemplates` → 目标对象、状态、复合子项。
- `CashFlowForecast + GoalPolicy` → `AllocationEngine` 的输入。
- `Reports` → 从领域数据导出只读汇总；不能成为第二本账。
- `FeatureConfiguration + Onboarding` → UI 展示与推荐，不控制服务端权限。

### 7.5 初版主要领域对象
- `User`, `Household`, `Membership`, `FeaturePreference`, `OnboardingAnswer`。
- `Account`, `Currency`, `ExchangeRateSnapshot`, `Transaction`, `JournalEntry`, `Category`。
- `Budget`, `BudgetLine`, `BudgetPeriod`, `BudgetRevision`, `FinancialSnapshot`。
- `Goal`, `GoalComponent`, `GoalTemplateDefinition`, `GoalStatusEvent`。
- `FundingSource`, `GoalAllocation`, `AllocationPlan`, `AllocationDecision`。
- `CashFlowProjection`, `RecurringRule`, `AlgorithmVersion`, `Scenario`, `AuditEvent`。

将 `Household` 与个人数据归属的模型从最初建立，哪怕首版只支持单用户；后期家庭共享只增加权限和协作，不迁移无归属数据。

### 7.6 财务数据不变量（必须测试）
1. 账户转账不得增加家庭净资产。
2. 虚拟资金池分配不得改变真实账户余额。
3. 目标分配金额不得超过该资金来源的可归属余额。
4. 购买基金不等于消费，卖出基金不等于全部是盈利。
5. 报表不能把换汇和市场估值差异直接算作工资或经营收入。
6. 交易/目标/预算的用户归属必须在服务端验证。
7. 所有财务变动可审计；重要记录更正可重放/对账。
8. 多币种金额具有明确货币精度、估值日期和舍入规则。
9. 往期预算报告可以依据历史快照复现，不随新模板悄然改变。
10. 计算结果在相同输入、算法版本和参数下确定且可复测。

### 7.7 安全下限
- `MockAuth` 只能用于开发或显式测试环境；生产构建默认拒绝该模式。
- 正式认证上线前不允许公开收集真实财务数据；所有 API 强制鉴权及逐资源授权。
- 防暴力登录和会话窃取，CSRF/同源策略、密码/凭证保护；不在日志写入完整个人收支。
- 数据最少化、用户可导出/删除、定期备份与恢复演练、配置密钥隔离。
- 以 OWASP ASVS 5.0 为安全验收基准，具体控制映射在第二交付完成。

## 9. 技术风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 功能范围过大 | 永远做不完，UI 混乱 | 完整规划、只开发 P0、每阶段有可运行产物 |
| 评分看似科学但参数任意 | 用户误信结果 | 来源区分方法/假设，提供解释与用户控制 |
| 复杂优化超免费服务器 CPU | 超时或成本提高 | MVP 用确定性规则；重型优化使用隔离计算执行环境 |
| D1/SQLite 与未来 PostgreSQL 差异 | 数据库迁移有成本 | Repository 抽象 + 正式 schema migrations + SQL 方言测试 |
| 模拟认证错误上线 | 严重隐私泄露 | 构建/部署时硬性禁止 Mock Auth；正式鉴权前不收真实财务数据 |
| 家庭成员账户互相可见 | 数据泄露 | 明确 owner/household 所有权和逐资源授权 |
| 目标资金与账户余额双计数 | 财务报表失真 | 虚拟 earmark 与真实交易分离；不可违反的不变量测试 |
| 多币种与投资收益混淆 | 资产增长失真 | 原币/估值币/收益来源分解；固定汇率日期 |
| 退休预算切换丢历史 | 破坏长期可审计性 | 预算版本化，状态切换只新增事件和新版本 |
| 低活跃免费服务不稳定 | 数据不可用 | 备份恢复、监控、平台配额测试、付费升级预案 |

## 10. 待确认的产品决策（第二交付前必须冻结）

| 编号 | 决策点 | 我的默认建议 | 是否影响架构 |
|---|---|---|---|
| D-01 | 用户端首发范围 | 先 Web、以后 Tauri/小程序 | 低（接口设计阶段需预留） |
| D-02 | 活跃目标数量 | **硬上限 3 个顶层目标**；子目标不计 | 高（GoalPolicy） |
| D-03 | 紧急目标是否自动暂停旧目标 | **只建议，不自动执行** | 高（审计和状态机） |
| D-04 | 应急金/必要偿债是否占目标名额 | **不占；作为硬约束** | 高（资金可用性） |
| D-05 | 家庭多人协作是否初版上线 | **预留模型，初版只做个人使用** | 高（权限） |
| D-06 | 多币种 | **底层一开始支持原币，自动行情与复杂 FX 后做** | 高（金额模型） |
| D-07 | 财务账本 | **账户+平衡分录内核，UI 只展示简单收支** | 高（永久数据模型） |
| D-08 | 目标池能否自由借用资金 | **仅用户显式确认可转移；来源必须合法可用** | 高（目标关联） |
| D-09 | 目标推荐问卷程度 | **3 屏初次引导 + 情境问卷** | 中（体验） |
| D-10 | 退休何时进入支出期 | **事件触发，用户确认，版本化预算** | 中（生命周期） |
| D-11 | 算法自动化程度 | **确定性规则先行，LP/MILP 后做** | 高（引擎） |
| D-12 | 生产认证时间 | **本地先模拟，公开收真实数据前真认证** | 高（上线门槛） |
| D-13 | 开源还是闭源 | **暂按未来可能闭源，审查依赖许可证** | 中（库选择） |
| D-14 | 数据存储优先级 | **首版云端 D1，后续加离线支持** | 高（同步模型） |
| D-15 | 投资收益计算范围 | **先账户余额及明确记录，后加持仓回报分析** | 中（Asset 模块） |

本轮讨论优先解决 D-02、D-04、D-05、D-07、D-08、D-12、D-14。这些决定的修改代价最大。其余可按默认提案先继续。
